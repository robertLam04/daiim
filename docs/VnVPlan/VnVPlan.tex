\section{General Information}

\subsection{Summary}

The software being tested is DAIIM (Decentralized Artificial Intelligence Inference Marketplace), a decentralized platform that allows users to submit artificial intelligence (AI) inference requests and receive aggregated predictions from multiple independent inference providers.
The system enables task requesters to submit inference requests for supported machine learning tasks, while inference providers can register for tasks, contribute predictions, and receive compensation for their participation. The platform uses smart contracts deployed on a public blockchain to manage core marketplace operations, including provider registration, staking, request payments, result aggregation, reputation updates, and reward distribution.
The system also includes a web-based user interface for interacting with the marketplace, an off-chain backend for coordinating inference requests and communicating with providers, and a database for storing relevant off-chain information. By combining on-chain and off-chain components, DAIIM aims to provide a transparent and decentralized marketplace that reduces reliance on centralized AI inference providers.


\subsection{Objectives}

The objective of this Verification and Validation (V\&V) plan is to build confidence in the correctness, reliability, and usability of the DAIIM platform by verifying that its implemented components satisfy the requirements defined in the Software Requirements Specification (SRS).

Verification will focus on ensuring that the marketplace correctly handles the submission and validation of inference requests, provider registration and participation, prediction collection, result aggregation, and financial settlement. Particular attention will be given to the interactions between the on-chain smart contracts and off-chain components, ensuring that transactions and marketplace state changes are handled consistently and correctly.


Reliability will also be an important focus of the V\&V activities. Testing will examine whether the system can produce aggregated results when multiple providers participate, including scenarios where some providers are unavailable or submit inaccurate predictions. This will help evaluate whether the aggregation and reputation mechanisms behave as intended under different provider conditions.

Usability validation will focus on whether users can interact with the marketplace without requiring extensive knowledge of blockchain technology or machine learning. This includes evaluating whether users can submit inference requests, authorize transactions, monitor request progress, and understand the resulting predictions and associated information.

The V\&V plan will primarily be derived from the Software Requirements Specification (SRS), which defines the functional and non-functional requirements used to construct system-level test cases. The Hazard Analysis will also guide testing priorities by identifying potential failures involving inference reliability, transaction integrity, security, availability, and incentive mechanisms. System architecture and design documentation will further support test development by identifying component interactions, data flows, and interfaces that require verification.

Due to project time and resource constraints, certain verification activities will be outside the scope of this plan. The internal correctness of external dependencies, such as the blockchain network, wallet software, and third-party infrastructure, will not be independently verified. Instead, testing will focus on ensuring that DAIIM integrates with and uses these dependencies correctly. Similarly, the internal implementation and predictive capabilities of individual providers' machine learning models will not be independently validated. Testing will instead focus on the collection and aggregation of provider predictions and the resulting marketplace behaviour.


\subsection{Custom Documents}

The project includes two approved Custom Documents (CDs):

\begin{itemize}
    \item \textbf{Cognitive Walkthrough:} A cognitive walkthrough will be conducted using a wireframe prototype of the planned application interface, from the perspective of inference requesters. This activity will help identify usability issues and areas of ambiguity in the user workflow. The findings will support validation of whether the interface is understandable and learnable, particularly for users with limited experience in blockchain technology or machine learning.

    \item \textbf{Business Plan:} A business plan will be developed following the completion of a successful proof of concept. It will describe the proposed business model and market strategy for DAIIM, including the potential market need, cost breakdown, competition, tokenomics, and execution plan. Although this document does not directly contribute to software verification, it provides additional context regarding the intended operation and long-term objectives of the marketplace.
\end{itemize}

\subsubsection{Accounts and Authentication}

These tests verify the account authentication requirements in the
\href{../SRS/SRS.pdf}{SRS}, including authentication with a compatible Web3
wallet extension and an embedded wallet.
		
\paragraph{Authentication Using a Web3 Wallet Extension}

\begin{enumerate}

\item{ST-AUTH-EXT-1\\}

Control: Manual

Initial State: The application is running in a supported browser on its public
page. A compatible Web3 wallet extension is installed and active. Test
profiles \texttt{EXT-USER-01} and \texttt{EXT-USER-02} are associated with
wallet fixtures \texttt{EXT-WALLET-01} and \texttt{EXT-WALLET-02}; neither
user is signed in.

Input:
\begin{itemize}
\item Connect \texttt{EXT-WALLET-01} and approve the verification-message
signature requested by the application.
\item Connect \texttt{EXT-WALLET-02} and approve its verification-message
signature.
\item Connect \texttt{EXT-WALLET-01} and reject the signature request.
\end{itemize}

Output:
\begin{itemize}
\item For the approved signature from \texttt{EXT-WALLET-01}, the user is
authenticated as \texttt{EXT-USER-01}, and that user's profile and
authenticated features are available.
\item For the approved signature from \texttt{EXT-WALLET-02}, the user is
authenticated as \texttt{EXT-USER-02}, and that user's profile and
authenticated features are available.
\item The user remains unauthenticated, no profile or authenticated features become available.
\end{itemize}

Test Case Derivation: FR1 requires the authentication
response to verify ownership of the connected wallet address.

How test will be performed: For each wallet, start from a signed-out session,
connect the specified extension account, and approve the verification-message
signature request. Confirm that \texttt{EXT-WALLET-01} opens
\texttt{EXT-USER-01}'s profile and \texttt{EXT-WALLET-02} opens
\texttt{EXT-USER-02}'s profile. Confirm that the user is granted access to the
authenticated features. Repeat the process and
reject the signature request; confirm that the user remains signed out and
cannot access authenticated features.

\item{ST-AUTH-EXT-2\\}

Control: Manual

Initial State: The application is running on its public page in a supported
browser. \texttt{EXT-WALLET-03} is available in a
compatible browser extension and is not yet associated with a DAIIM user
profile. The wallet owner is not signed in.

Input:
\begin{itemize}
\item Connect \texttt{EXT-WALLET-03} and approve the verification-message
signature.
\item Sign out of the resulting account.
\item Reconnect \texttt{EXT-WALLET-03} and approve the verification-message
signature again.
\end{itemize}

Output:
\begin{itemize}
\item After the first approved signature, the user is authenticated and a
profile is associated with \texttt{EXT-WALLET-03}. The system grants the user
access to authenticated features.
\item Sign-out ends the authenticated session; the user cannot access the
profile or authenticated features while signed out.
\item After the second approved signature, the same profile associated with
\texttt{EXT-WALLET-03} is displayed. No second profile is created for the
wallet. The system grants the user access to authenticated features.
\end{itemize}

Test Case Derivation: FR1 requires the system to
verify ownership of the wallet address and associate that verified address
with the same user profile on every successful authentication, including
after sign-out. The second successful authentication must restore
the profile created during the first sign-in.

How test will be performed: Record the number of DAIIM profiles associated
with \texttt{EXT-WALLET-03}. Connect the wallet and approve the
verification-message signature. Record the displayed profile identifier and
confirm that the wallet is associated with that profile. Sign out and verify
that the profile and authenticated features are no longer accessible. Sign in
again with the same wallet and approve the signature. Verify that the displayed
profile identifier matches the recorded identifier and that the number of
profiles associated with the wallet has not increased.

\end{enumerate}

\item Submit \texttt{+15555550101} using the phone sign-in method.

\item Submit malformed email \texttt{not-an-email} using the email sign-in

\begin{itemize}
\item For each of the three supported identities, the system creates

\item For \texttt{not-an-email}, the system reports an input error, displays no

corresponding embedded-wallet sign-in method with the specified email
address, phone number, or social-account identity. For each successful case,
compare the displayed address with the configured mock address, verify that
the corresponding profile is authenticated, and confirm that exactly one
wallet was created. For the malformed email, enter it using the email sign-in
method and verify that the system reports an input error, does not call the
provider, and does not create a wallet or authenticated session.

Initial State: The application is running in a test environment, and existing

\texttt{EMB-RETURN-03} are signed out. Their embedded wallet addresses are
respectively \texttt{EMB-WALLET-RETURN-01},
\texttt{EMB-WALLET-RETURN-02}, and \texttt{EMB-WALLET-RETURN-03}. Configure

associated account.

Input:
\begin{itemize}
\item Enter \texttt{returning.email@example.test} using the email sign-in

\item Enter \texttt{+15555550102} using the phone sign-in method.
\item Provide social-account subject \texttt{social-return-03} using the

\item Enter \texttt{locked.user@example.test} using the email sign-in method.
\end{itemize}

Output:
\begin{itemize}
\item For \texttt{returning.email@example.test}, the system authenticates
\texttt{EMB-RETURN-01} and displays its existing profile and

\item For \texttt{+15555550102}, the system authenticates
\texttt{EMB-RETURN-02} and displays its existing profile and
\texttt{EMB-WALLET-RETURN-02}.
\item For social-account subject \texttt{social-return-03}, the system

\subsubsection{Reputation, Rewards, and Penalties}

These tests verify the reputation, reward, and penalty requirements
(FR35--FR48) and the safety requirements that protect reward and penalty
transfers (FR.SA.9, FR.SA.10). Each test follows a scenario that a group of
providers would go through on the real system: completing a request, misbehaving
during a request, and leaving a task. The tests run on a local Solana validator
or Solana Devnet, with mock inference providers that submit preset predictions,
so that the expected results can be worked out by hand before the test is run.
Boundary cases for each rule (such as a distance exactly equal to $\bar{d}$)
are covered by the unit tests.

The values of \texttt{SLASH\_FRACTION}, \texttt{MAX\_REPUTATION\_PENALTY},
\texttt{MINIMUM\_PROVIDER\_STAKE}, \texttt{REPEAT\_OFFENSE\_COUNT}, and
\texttt{REPEAT\_OFFENSE\_WINDOW} are defined in the SRS. The tests read them
from the deployed program's configuration, so they do not need to change if the
values change.

\begin{enumerate}

\item{ST-REP-1: Completed request updates reputations and pays rewards\\}

Control: Automatic

Initial State: A numerical regression task \texttt{Rep-Test-Task} exists with a
reputation tolerance $T = 2.0$. Mock providers \texttt{P1} to \texttt{P5} are
registered with reputation scores of 40, 60, 50, 50, and 50. A requester has
submitted an inference request with a payment of 1000 tokens held in escrow,
and all five providers have accepted it.

Input: The providers submit the valid predictions \texttt{P1}: 8.5,
\texttt{P2}: 11, \texttt{P3}: 12, \texttt{P4}: 13, \texttt{P5}: 20, and the
request runs to completion.

Output:
\begin{itemize}
\item The final aggregated result is 12. The distances from the result are
$d = (3.5, 1, 0, 1, 8)$, so $\bar{d} = 2.7$ and $\bar{d} + T = 4.7$.
\item \texttt{P2}, \texttt{P3}, and \texttt{P4} ($d_i \le 2.7$) have their
reputation increased. \texttt{P1} ($2.7 < 3.5 \le 4.7$) has an unchanged
reputation. \texttt{P5} ($8 > 4.7$) has its reputation decreased.
\item \texttt{P5} receives no reward. \texttt{P1} to \texttt{P4} share the 1000
tokens in proportion to their reputation scores (40, 60, 50, 50): 200, 300,
250, and 250 tokens.
\item The total paid out does not exceed 1000 tokens, the request's escrow is
empty afterwards, and the system logs a status check for each provider before
its reward is sent.
\end{itemize}

Test Case Derivation: FR35 requires $d_i$ and $\bar{d}$ to be computed for
every included provider, and FR37, FR38, and FR39 give the three possible
outcomes; this fixture places at least one provider in each. FR41 limits
rewards to providers whose reputation did not decrease, split by reputation, so
\texttt{P1} still qualifies and \texttt{P5} does not. FR.SA.9 forbids paying out
more than the reward, and FR.SA.10 requires each provider's status to be
checked before a reward is sent. The expected reward shares use the reputation
snapshot taken for aggregation (FR31); if the design uses the scores after the
update instead, the expected shares will be recomputed from those scores.

How test will be performed: Record each provider's reputation and token
balance, run the request, and read the result, the reputation scores, and the
reward transfers from both the application and the on-chain accounts. Assert
the values above, allowing up to one base unit of difference per reward for
integer rounding, and check the backend log for the status checks.

\item{ST-PEN-1: Misbehaving providers in a single request\\}

Control: Automatic

Initial State: Task \texttt{Penalty-Test-Task} has a numerical output schema.
Providers \texttt{P1} to \texttt{P5} are registered with 100 tokens of stake
each. \texttt{P1} has a reputation score of 100, and the others have 50. A
request has been submitted and all five providers have accepted it.

Input:
\begin{itemize}
\item \texttt{P1} and \texttt{P2} submit accurate predictions (10 and 10.5).
\item \texttt{P3} submits a valid but very inaccurate prediction (1{,}000{,}000).
\item \texttt{P4} submits a prediction that does not match the output schema (a
string instead of a number).
\item \texttt{P5} submits nothing, and the maximum prediction time is allowed
to pass.
\end{itemize}

Output:
\begin{itemize}
\item \texttt{P1}'s reputation is increased but stays at 100.
\item \texttt{P3}'s reputation decreases by no more than
\texttt{MAX\_REPUTATION\_PENALTY}, and its stake stays at 100 tokens.
\item \texttt{P4}'s prediction is rejected. \texttt{P4} and \texttt{P5} each
have their stake reduced to $100 \times (1 - \texttt{SLASH\_FRACTION})$ tokens
and their reputation decreased.
\item \texttt{P2}'s stake is unchanged, and every reputation score stays
within $[0, 100]$.
\end{itemize}

Test Case Derivation: FR43 requires slashing and a reputation decrease for a
rejected prediction, and FR44 requires the same for a provider that accepted
but did not submit. FR42 allows slashing only in those two cases, so the
inaccurate but valid prediction from \texttt{P3} must cost reputation and not
stake. FR40 caps the reputation decrease from a single request, which the
extreme prediction from \texttt{P3} checks. FR36 keeps scores within $[0,
100]$, which \texttt{P1} checks at the top of the range.

How test will be performed: Use a task with a short maximum prediction time.
Record each provider's stake and reputation, run the request until it
completes, and read the values again from the on-chain stake and reputation
accounts. Assert the expected values for each provider.

\item{ST-PEN-2: Providers leaving a task\\}

Control: Automatic

Initial State: Task \texttt{Exit-Test-Task} has an exit reputation threshold
$R_{\text{exit}} = 50$. The following providers are registered:
\begin{itemize}
\item \texttt{P1}: stake just above \texttt{MINIMUM\_PROVIDER\_STAKE}, so that
one slash drops it below the minimum.
\item \texttt{P2}: a large stake, so that slashing alone will not drop it below
the minimum during the test.
\item \texttt{P3}: a reputation score low enough that one decrease brings it to
0, and a stake of 100 tokens.
\item \texttt{P4}, \texttt{P5}, and \texttt{P6}: 100 tokens of stake each and
reputation scores of 80, 50, and 25.
\end{itemize}

Input:
\begin{itemize}
\item Run \texttt{REPEAT\_OFFENSE\_WINDOW} requests for the task. \texttt{P1}
fails to submit in the first one. \texttt{P2} fails to submit in
\texttt{REPEAT\_OFFENSE\_COUNT} of them. \texttt{P3} submits a very inaccurate
prediction in the first one. The other providers submit accurate predictions.
\item After the requests finish, \texttt{P4}, \texttt{P5}, and \texttt{P6}
voluntarily unregister.
\item While one of the requests is active, \texttt{P4} tries to unregister.
\end{itemize}

Output:
\begin{itemize}
\item \texttt{P1} is unregistered automatically after its stake falls below
\texttt{MINIMUM\_PROVIDER\_STAKE}.
\item \texttt{P2} is unregistered after its \texttt{REPEAT\_OFFENSE\_COUNT}-th
slash, and its remaining stake is burned.
\item \texttt{P3}'s reputation reaches 0. \texttt{P3} is unregistered and its
remaining stake is burned.
\item \texttt{P4}'s attempt to unregister during an active request is refused.
After the requests, \texttt{P4} ($R = 80$) and \texttt{P5} ($R = 50 =
R_{\text{exit}}$) get all 100 tokens back. \texttt{P6} ($R = 25$) gets
$\frac{25}{50} \times 100 = 50$ tokens back, and the other 50 are burned.
\end{itemize}

Test Case Derivation: FR45, FR46, and FR47 give the three cases where a
provider is removed automatically: stake below the minimum, too many slashes,
and a reputation of 0. FR46 and FR47 also require the remaining stake to be
burned. FR48 sets how much stake is returned on voluntary unregistration, and
\texttt{P5} sits exactly on the threshold. The refused attempt by \texttt{P4}
also exercises FR15.

How test will be performed: After each request, record each provider's
registration status, stake, and slash count. Record the total burned token
supply and each provider's token balance before and after unregistration, and
assert the expected changes.

\end{enumerate}

\subsubsection{Transparency and Data Handling}

These tests verify that users can see and verify the transactions they
authorize (FR49--FR52) and that a request's input data is protected for its
whole life (FR53--FR55). They follow a requester who pays for a request and
checks it, and a request's input data from submission to deletion.

\begin{enumerate}

\item{ST-TRANS-1: Requester pays for a request and verifies it\\}

Control: Automatic

Initial State: An authenticated requester is signed in with a test wallet
signer that holds 50 tokens. Task \texttt{Rep-Test-Task} and the providers from
ST-REP-1 are registered.

Input:
\begin{itemize}
\item Submit an inference request with a payment of 137 tokens.
\item Add funds so the wallet holds 1000 tokens, then submit the request again
and approve the transaction.
\item Let the request run to completion, then open the transaction history.
\end{itemize}

Output:
\begin{itemize}
\item On the first attempt, the system shows an insufficient-funds error and
does not ask the wallet for a signature.
\item On the second attempt, before the wallet asks for a signature, the
application shows the action (``Submit inference request'') and the amount
(137 tokens).
\item The transaction status is shown as pending and then confirmed.
\item The requester's token balance goes down by exactly 137 tokens, and the
request's escrow holds exactly 137 tokens.
\item The transaction history shows an identifier for the payment. Looking it
up on Solana Devnet returns a transaction signed by the requester's wallet
with the expected instruction and amount.
\item The blockchain holds records of the payment, the providers' stakes, the
aggregated result, the reputation updates, and the reward transfers, and each
matches the value shown in the application.
\end{itemize}

Test Case Derivation: FR.SA.2 requires a balance check before a signature is
requested. FR49 requires the action and amount to be shown before signing, and
FR50 requires the status to be shown until it is final. FR.SA.8 requires the
amount charged to equal the amount approved; an unusual amount (137) is used so
that a hard-coded or rounded value would be caught. FR51 requires an identifier
that can be looked up on the blockchain, and FR52 lists the records that must
be on the blockchain.

How test will be performed: Run the flow in an automated browser test. Pause
the test wallet signer when it receives a signing request and check the
confirmation screen. Record each status shown. Compare balances before and
after. Query Solana Devnet with the transaction identifier and read the
request, stake, and reputation accounts directly, without going through the
application's backend.

\item{ST-DATA-1: Input data from submission to deletion\\}

Control: Automatic

Initial State: Task \texttt{Data-Test-Task} has registered providers
\texttt{P1}, \texttt{P2}, and \texttt{P3}. Another authenticated user
\texttt{U1} is not involved.

Input:
\begin{itemize}
\item Requester \texttt{R1} submits request \texttt{REQ-A} whose input contains
the marker value \texttt{271828.1828}. \texttt{P1} and \texttt{P2} accept it;
\texttt{P3} does not.
\item During the prediction phase, \texttt{R1}, \texttt{P1}, \texttt{P2},
\texttt{P3}, \texttt{U1}, and an unauthenticated client each try to get the
input data.
\item \texttt{REQ-A} runs to completion.
\item \texttt{R1} submits request \texttt{REQ-B}, which is cancelled because
too few providers accept it.
\end{itemize}

Output:
\begin{itemize}
\item Only \texttt{R1}, \texttt{P1}, and \texttt{P2} can get \texttt{REQ-A}'s
input. \texttt{P3}, \texttt{U1}, and the unauthenticated client are refused.
\item No transaction or account linked to either request contains the marker
value in readable form.
\item After each request reaches its final state, its input is no longer in
any storage the system controls, and every user, including \texttt{R1}, gets
``not found'' when asking for it.
\end{itemize}

Test Case Derivation: FR53 limits the input to the requester and the providers
that accepted; \texttt{P3} checks that being registered is not enough. FR54
forbids readable input on the blockchain, and the marker value makes it
possible to search raw on-chain data for it. FR55 requires deletion after both
completion and cancellation. The test also exercises FR24 (input given to
accepting providers) and FR23 (cancellation when too few providers accept).

How test will be performed: Call the input-data endpoint as each user. Search
the raw data of every linked transaction and account for the marker in its
common encodings (text, 32-bit and 64-bit floating point, and the program's
fixed-point format). After each request ends, query the database, file
storage, and caches directly and through the application.

\end{enumerate}

\subsubsection{Safety}

This test verifies the transaction safety requirements that are not already
covered by the tests above (FR.SA.1 and FR.SA.3--FR.SA.7). FR.SA.2 and FR.SA.8
are covered by ST-TRANS-1, and FR.SA.9 and FR.SA.10 by ST-REP-1. The test
injects faults using a test build of the backend and a proxy between the
system and the Solana RPC.

\begin{enumerate}

\item{ST-SAFE-1: Requester payments under transaction faults\\}

Control: Automatic, with the retry step also checked manually in the web client

Initial State: A requester is signed in with 1000 tokens. The RPC proxy and
the backend test build can each be set to inject one fault.

Input: The requester submits an inference request payment several times, with
a different fault each time:
\begin{enumerate}
\item The proxy forwards the transaction but drops the response.
\item The proxy holds the transaction until its blockhash has expired.
\item The requester's tokens are moved out of the wallet after the balance
check but before the transaction runs.
\item The requester rejects the signature, and separately a test script sends
a payment signed by a different wallet directly to the program.
\item The backend test build changes the transaction's amount after the amount
has been shown to the user.
\item After any of the failures above, the requester presses retry.
\end{enumerate}

Output:
\begin{enumerate}
\item The system checks the status before trying again, finds the payment was
processed, and does not resubmit. Exactly one payment is made and each status
is logged.
\item The system only marks the payment as failed after the validity period
has ended and it has checked the status.
\item The on-chain program rejects the payment and no state changes.
\item The rejected signature is never submitted, and the program rejects the
payment signed by the wrong wallet.
\item The simulation does not match the shown amount, so the transaction is not
sent for signing.
\item The user sees an error message with an option to retry, and the retry
succeeds.
\end{enumerate}

Test Case Derivation: Each fault matches one requirement: FR.SA.1 (no
resubmission before confirming the first was not processed, with status logs),
FR.SA.5 (wait for expiry and a status check), FR.SA.3 (the on-chain program
checks funds at execution), FR.SA.4 (only signed transactions are submitted),
FR.SA.7 (simulation must match the shown amounts), and FR.SA.6 (show the error
and allow a retry). After the whole test, the requester should have paid only
for the requests that succeeded.

How test will be performed: Run each fault in turn. Use the proxy to count
submitted transactions and the test wallet signer to count signing requests.
Count payments from the requester's wallet on Devnet and compare the final
balance with the number of successful requests. A tester also runs step 6 by
hand in the web client and records the error message shown.

\end{enumerate}

\subsubsection{Accuracy, Reliability, and Scalability}

\begin{enumerate}

\item{NFR-SIM-1: Large-scale request simulation\\}

Control: Automatic

Initial State: The system runs on a local Solana validator with a simulation
harness that controls mock providers and can inject faults. A separate
reference implementation of the Appendix A aggregation algorithm is written
in TypeScript by a team member who did not write the system's version.

Input/Condition:
\begin{itemize}
\item Run \texttt{NUM\_SIMULATED\_REQUESTS} requests with random predictions
and reputation scores, including values at the edges of their declared ranges
(reputation 0 and 100, the largest and smallest allowed predictions and token
amounts) and the worked examples from the SRS.
\item Mix in failure scenarios: too few providers accept, too few valid
predictions, providers that do not submit, invalid predictions, dropped or
delayed RPC responses, and a backend restart during the prediction phase.
\item Run the requests at 1, 5, 10, 20, and \texttt{MAX\_CONCURRENT\_REQUESTS}
at the same time. Mock providers reply immediately, so only the system's own
processing time is measured.
\item During each prediction phase, try to read submitted predictions as
another provider, as the requester, and from the raw on-chain data.
\end{itemize}

Output/Result:
\begin{itemize}
\item Every aggregated result equals the reference implementation's result.
The test reports the number of mismatches (expected: 0).
\item No calculation overflows. Any input that would overflow causes the
transaction to fail with no change to on-chain state.
\item Every request reaches a final state before its final deadline, and its
escrow is empty afterwards.
\item No prediction can be read before its prediction phase ends.
\item A table and graph of the median and 95th-percentile processing time at
each concurrency level. The test passes if the median at
\texttt{MAX\_CONCURRENT\_REQUESTS} is no more than
\texttt{PERFORMANCE\_DEGRADATION\_TOLERANCE} higher than for a single request.
\end{itemize}

Test Case Derivation: NFR1 requires simulation tests to show that the results
match the Appendix A algorithm. NFR2 forbids overflow and requires an
overflowing transaction to leave no change. NFR13 requires every request to
reach a final state and settle its escrow before the final deadline. NFR11
requires predictions to stay hidden until the phase ends. NFR15 requires
concurrent requests without a drop in performance.

How test will be performed: The harness runs the requests and then reads each
request's status, result, and escrow from the blockchain. It compares each
result with the reference implementation and logs the inputs of any mismatch
so they can be added as a unit test. It checks that the tokens escrowed at the
start equal the tokens paid out, returned, slashed, and burned. Each
concurrency level is run 3 times, and the timings come from the system's logs.

\end{enumerate}

\subsubsection{Usability}

\begin{enumerate}

\item{NFR-USE-1: Usability study with new users\\}

Control: Manual, with timing checks automated

Initial State: The web application is deployed on a test environment
connected to Solana Devnet. 5 to 8 participants who use a web browser but have
never used a blockchain wallet or built a machine learning model are recruited.

Input/Condition: Each participant gets a short description of DAIIM, but no
instructions on how to use it, and completes these tasks while thinking out
loud:
\begin{enumerate}
\item Sign in by creating an embedded wallet with an email address.
\item Find the documentation and the list of available tasks.
\item Submit an inference request for an existing task.
\item Find the result of the request and the payment for it.
\item Sign out.
\end{enumerate}
During task 3, the test build forces one error (a failed transaction). The
participant then fills out the survey in the Usability Survey Questions
appendix.

Output/Result:
\begin{itemize}
\item At least \texttt{USABILITY\_COMPLETION\_RATE} of participants complete
every task without help, including creating a wallet with no Web3 knowledge.
\item The median time to finish tasks 1 to 3 is 5 minutes or less.
\item Every feature can be reached within 2 clicks of the home page.
\item Every error shown has a name, a description, and a suggested fix, and
appears within 2 seconds of the failure being detected.
\item A progress indicator is shown during every operation longer than
\texttt{LONG\_OPERATION\_THRESHOLD}.
\item A plain-language confirmation is shown after every transaction.
\item The survey results are summarized in a table and bar chart.
\end{itemize}

Test Case Derivation: NFR3 requires a new user to learn the system within 5
minutes, and NFR8 requires them to create an embedded wallet without Web3
knowledge. NFR4 requires every feature within 2 clicks. NFR5 requires errors to
have a name, description, and fix, and NFR.SA.1 requires them within 2 seconds.
NFR6 requires progress to be shown for long operations, and NFR7 requires
plain-language confirmations.

How test will be performed: A team member observes each session, times each
task, records clicks, and only helps if the participant is stuck for more than
3 minutes (which counts as not completing the task). A team member also
counts the clicks to each feature from the home page. Error timings and
progress indicators are checked by an automated browser test that repeats the
same tasks with forced errors and delays. One study is held after the Rev 0
demo and a second after changes are made in response to it.

\end{enumerate}

\subsubsection{Security, Privacy, and Safety}

\begin{enumerate}

\item{NFR-SEC-1: Security and privacy audit\\}

Control: Manual, with automated scans

Initial State: The system is deployed in its test environment. A request is in
progress, so its input data is stored. Test providers have consented to
showing different sets of profile information.

Input/Condition:
\begin{itemize}
\item Run a full request with an extension wallet and with an embedded wallet,
capturing network traffic and backend logs.
\item Read the raw contents of the database and file storage.
\item Scan every endpoint's TLS setup, connect over plain HTTP, and point the
backend at RPC and storage endpoints that use a self-signed certificate.
\item Visit every public page without signing in.
\end{itemize}

Output/Result:
\begin{itemize}
\item Input data is encrypted in all captured traffic and cannot be read in
raw storage, using algorithms and key lengths on a recognized recommended list
(for example, NIST SP 800-175B).
\item All endpoints use TLS 1.2 or later with valid certificates. Plain HTTP
is refused or redirected, and the backend refuses endpoints with invalid
certificates.
\item No private key or recovery phrase appears in traffic, logs, or storage,
and no email address or phone number appears on the blockchain.
\item Public pages show only the information each provider agreed to share.
\item A completed audit checklist based on the PIPEDA safeguards principle,
with any gaps recorded as issues.
\end{itemize}

Test Case Derivation: NFR9 and NFR10 require sensitive data to be encrypted in
transit and at rest to an industry standard, verified through a security
audit. NFR.SA.3 requires TLS with certificate checks. NFR.SA.2 requires all
signing to happen in the user's wallet with no private information on the
blockchain. NFR12 limits public pages to information providers consented to.

How test will be performed: A team member who did not write the storage code
leads the audit. Search the captured traffic, logs, storage, and on-chain data
for marker values in the input and for the test wallets' keys and the test
users' contact details. Run \texttt{testssl.sh} against each endpoint. Compare
each public page with the providers' consent settings. The team reviews the
checklist in a meeting.

\end{enumerate}
