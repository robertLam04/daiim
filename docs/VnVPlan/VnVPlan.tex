\section{Introduction}

This document presents the Verification and Validation (V\&V) Plan for DAIIM.
It describes the activities that will be used to increase confidence that the
implemented system satisfies its functional and non-functional requirements. The plan
identifies the documents, people, tools, environments, and testing methods that
will support verification and validation throughout development.

The remainder of this document is organized as follows. The
General Information section summarizes the system, defines the
objectives of the V\&V activities, and identifies the related project
documents. The Plan section describes the V\&V team and the planned
approaches for verifying the SRS, the system design, this V\&V plan, the implementation
and the tools used in the validation process. 
The System Tests section specifies the tests of the
integrated system, including tests for functional and non-functional
requirements and the traceability between requirements and test cases. The
Unit Test Description section outlines the scope and planned
organization of unit-level testing and its relationship to the system
modules. The appendices provide symbolic test parameters, usability
survey questions, the Generative AI Use Disclosure, and a reflection on the
V\&V deliverable.

\section{General Information}

\subsection{Summary}

The software being tested is DAIIM (Decentralized Artificial Intelligence Inference Marketplace), a decentralized platform that allows users to submit artificial intelligence (AI) inference requests and receive aggregated predictions from multiple independent inference providers.
The system enables task requesters to submit inference requests for supported machine learning tasks, while inference providers can register for tasks, contribute predictions, and receive compensation for their participation. The platform uses smart contracts deployed on a public blockchain to manage core marketplace operations, including provider registration, staking, request payments, result aggregation, reputation updates, and reward distribution.
The system also includes a web-based user interface for interacting with the marketplace, an off-chain backend for coordinating inference requests and communicating with providers, and a database for storing relevant off-chain information. By combining on-chain and off-chain components, DAIIM aims to provide a transparent and decentralized marketplace that reduces reliance on centralized AI inference providers.


\subsection{Objectives}

The objective of this Verification and Validation (V\&V) plan is to build confidence in the correctness, reliability, and usability of the DAIIM platform by verifying that its implemented components satisfy the requirements defined in the Software Requirements Specification (SRS).

Verification will focus on ensuring that the marketplace correctly handles the submission and validation of inference requests, provider registration and participation, prediction collection, result aggregation, and financial settlement. Particular attention will be given to the interactions between the on-chain smart contracts and off-chain components, ensuring that transactions and marketplace state changes are handled consistently and correctly.


Reliability will also be an important focus of the V\&V activities. Testing will examine whether the system can produce aggregated results when multiple providers participate, including scenarios where some providers are unavailable or submit inaccurate predictions. This will help evaluate whether the aggregation and reputation mechanisms behave as intended under different provider conditions.

Usability validation will focus on whether users can interact with the marketplace without requiring extensive knowledge of blockchain technology or machine learning. This includes evaluating whether users can submit inference requests, authorize transactions, monitor request progress, and understand the resulting predictions and associated information.

The V\&V plan will primarily be derived from the Software Requirements Specification (SRS), which defines the functional and non-functional requirements used to construct system-level test cases. The Hazard Analysis will also guide testing priorities by identifying potential failures involving inference reliability, transaction integrity, security, availability, and incentive mechanisms. System architecture and design documentation will further support test development by identifying component interactions, data flows, and interfaces that require verification.

Due to project time and resource constraints, certain verification activities will be outside the scope of this plan. The internal correctness of external dependencies, such as the blockchain network, wallet software, and third-party infrastructure, will not be independently verified. Instead, testing will focus on ensuring that DAIIM integrates with and uses these dependencies correctly. Similarly, the internal implementation and predictive capabilities of individual providers' machine learning models will not be independently validated. Testing will instead focus on the collection and aggregation of provider predictions and the resulting marketplace behaviour.


\subsection{Custom Documents}

The project includes two approved Custom Documents (CDs):

\begin{itemize}
    \item \textbf{Cognitive Walkthrough:} A cognitive walkthrough will be conducted using a wireframe prototype of the planned application interface, from the perspective of inference requesters. This activity will help identify usability issues and areas of ambiguity in the user workflow. The findings will support validation of whether the interface is understandable and learnable, particularly for users with limited experience in blockchain technology or machine learning.

    \item \textbf{Business Plan:} A business plan will be developed following the completion of a successful proof of concept. It will describe the proposed business model and market strategy for DAIIM, including the potential market need, cost breakdown, competition, tokenomics, and execution plan. Although this document does not directly contribute to software verification, it provides additional context regarding the intended operation and long-term objectives of the marketplace.
\end{itemize}

\subsection{Relevant Documentation}

The following documents provide essential background and guidance for the V\&V activities:

\begin{enumerate}
    \item \textbf{Software Requirements Specification (SRS):} The SRS defines the functional and non-functional requirements of DAIIM. It serves as the primary reference for developing system-level test cases and determining the expected behaviour of the implemented software.

    \item \textbf{Hazard Analysis (HA):} The Hazard Analysis identifies potential system-level hazards, their causes, and their consequences. It helps prioritize verification activities toward areas where failures could have significant effects, including inference accuracy and reliability, transaction integrity, provider security, and financial settlement.
\end{enumerate}

\textbf{Input:}

\item[3.] Reconnect \fixture{EXT-WALLET-03} and approve the verification-message

request to be Completed once every reward transfer has succeeded. \saref{SA_RewardValidation} forbids paying out
more than the reward, and \saref{SA_ProviderStatusCheck} requires each provider's status to be
checked before a reward is sent. The expected reward shares use the reputation
snapshot taken for aggregation (\rref{FR_PredictionAggregation}); if the design uses the scores after the
update instead, the expected shares will be recomputed from those scores.

\textbf{How test will be performed:} Record each provider's reputation and token
balance, run the request, and read the result, the reputation scores, and the
reward transfers from both the application and the on-chain accounts. Assert
the values above, allowing up to one base unit of difference per reward for
integer rounding, and check the backend log for the status checks.

\item{ST-REP-2: A reward transfer fails and is held\\}

\textbf{Control:} Automatic

\textbf{Initial State:} The same task, providers, and request as ST-REP-1, with
two changes: \fixture{P2}'s token account is closed before rewards are
distributed, so it cannot receive tokens, and \fixture{P3}'s token account is
also closed. The test controls the validator's clock so that time can be moved
forward past the pending transfer deadline.

\textbf{Input:}
\begin{itemize}
\item[1.] The providers submit the same predictions as ST-REP-1, and the
request reaches reward distribution.
\item[2.] \fixture{P2} opens a new token account and retries its reward transfer
from the provider dashboard before the pending transfer deadline.
\item[3.] \fixture{P3} does nothing, and the clock is moved past the pending
transfer deadline (end of the reveal phase plus
\fixture{PENDING\_TRANSFER\_PERIOD}).
\end{itemize}

\textbf{Output:}
\begin{itemize}
\item[1.] \fixture{P1} and \fixture{P4} receive their rewards (200 and 250
tokens). The 300 tokens for \fixture{P2} and the 250 tokens for \fixture{P3} stay
in the request's escrow, both transfers are recorded as unresolved, and the
request's status is Pending Transfer. The requester can still see the final
aggregated result.
\item[2.] \fixture{P2} and \fixture{P3} each receive a notification, and each of
their dashboards shows the held reward amount and the pending transfer
deadline.
\item[3.] After the retry, \fixture{P2}'s new token account holds the 300 tokens
and \fixture{P2}'s transfer is recorded as resolved. The request stays in
Pending Transfer because \fixture{P3}'s transfer is still unresolved.
\item[4.] After the deadline, \fixture{P3}'s 250 tokens are burned (the total
burned supply increases by 250), \fixture{P3}'s transfer is recorded as
forfeited, and the request's status changes to Completed.
\end{itemize}

\textbf{Test Case Derivation:} \rref{FR_RewardTransferFailure} requires a failed transfer to be held in escrow and
recorded as unresolved, with the request set to Pending Transfer, while other
transfers and the result are not affected. \rref{FR_PendingTransferNotice} requires a notification and the
dashboard details. \rref{FR_PendingTransferRetry} allows the provider to retry before the deadline, and
\rref{FR_PendingTransferDeadline} requires the held reward to be burned at the deadline. \rref{FR_RequestCompletion} only
allows the request to become Completed once every transfer has succeeded or
been forfeited, which is why it stays in Pending Transfer after
\fixture{P2}'s retry.

\textbf{How test will be performed:} After each input step, read the request's
status, the escrow balance, each provider's token balance, the transfer
records, and the total burned supply from the blockchain, and check each
provider's notifications and dashboard in the application.

\item{ST-PEN-1: Misbehaving providers in a single request\\}

\textbf{Control:} Automatic

\textbf{Initial State:} Task \fixture{Penalty-Test-Task} has a numerical output schema.
Providers \fixture{P1} to \fixture{P5} are registered with 100 tokens of stake
each. \fixture{P1} has a reputation score of 100, and the others have 50. A
request has been submitted and all five providers have accepted it.

\textbf{Input:}
\begin{itemize}
\item[1.] \fixture{P1} and \fixture{P2} submit predictions close to each other (10
and 10.5).
\item[2.] \fixture{P3} submits a valid prediction far from the others
(1{,}000{,}000).
\item[3.] \fixture{P4} submits a prediction that does not match the output schema (a
string instead of a number).
\item[4.] \fixture{P5} submits nothing, and the protocol-wide COMMIT\_PERIOD and REVEAL\_PERIOD are allowed
to pass.
\end{itemize}

\textbf{Output:}
\begin{itemize}
\item[1.] The final aggregated result is 10.25. \fixture{P1}'s reputation stays at
100, and \fixture{P2}'s reputation increases.
\item[2.] \fixture{P3}'s reputation decreases by no more than
\fixture{MAX\_REPUTATION\_PENALTY}, and its stake stays at 100 tokens.
\item[3.] \fixture{P4}'s prediction is rejected. \fixture{P4} and \fixture{P5} each
have their stake reduced to $100 \times (1 - \fixture{SLASH\_FRACTION})$ tokens
and their reputation decreased.
\item[4.] \fixture{P1}'s and \fixture{P2}'s stakes are unchanged, and every
reputation score is within $[0, 100]$.
\end{itemize}

\textbf{Test Case Derivation:} The result of 10.25 follows from the weighted-median
algorithm (\rref{FR_PredictionAggregation}): \fixture{P1}, \fixture{P2}, and \fixture{P3} are included with weights
0.5, 0.25, and 0.25, and the running total is exactly 0.5 after 10, so the
result is the average of 10 and 10.5. \rref{FR_SlashInvalidPrediction} requires slashing and a reputation
decrease for a rejected prediction, and \rref{FR_SlashNoCommit}, \rref{FR_SlashNoReveal} requires the same for a provider that
accepted but did not submit. \rref{FR_InferenceProviderSlashing} allows slashing only in those two cases, so the
valid prediction from \fixture{P3} must cost reputation and not stake.
\rref{FR_ReputationRange} keeps scores within $[0, 100]$, which
\fixture{P1} checks at the top of the range.

\textbf{How test will be performed:} Use a test protocol configuration with short COMMIT\_PERIOD and REVEAL\_PERIOD values.
Record each provider's stake and reputation, run the request until it
completes, and read the values again from the on-chain stake and reputation
accounts. Assert the expected values for each provider.

\item{ST-PEN-2: Providers leaving a task\\}

\textbf{Control:} Automatic

\textbf{Initial State:} Task \fixture{Exit-Test-Task} has an exit reputation threshold
$R_{\text{exit}} = 50$. The following providers are registered:
\begin{itemize}
\item \fixture{P1}: stake just above \fixture{MINIMUM\_PROVIDER\_STAKE}, so that
one slash drops it below the minimum.
\item \fixture{P2}: a large stake, so that slashing alone will not drop it below
the minimum during the test.
\item \fixture{P3}: a reputation score low enough that one decrease brings it to
0, and a stake of 100 tokens.
\item \fixture{P4}, \fixture{P5}, and \fixture{P6}: 100 tokens of stake each and
reputation scores of 80, 50, and 25.
\end{itemize}

\textbf{Input:}
\begin{itemize}
\item[1.] Run \fixture{REPEAT\_OFFENSE\_WINDOW} requests for the task. In every
request, most providers submit predictions close to 50. \fixture{P1} submits
nothing in the first request. \fixture{P2} submits nothing in
\fixture{REPEAT\_OFFENSE\_COUNT} of the requests. \fixture{P3} submits a
prediction far from the others (5000) in the first request.
\item[2.] While one of the requests is active, \fixture{P4} tries to unregister.
\item[3.] After the requests finish, \fixture{P4}, \fixture{P5}, and \fixture{P6}
voluntarily unregister.
\end{itemize}

\textbf{Output:}
\begin{itemize}
\item[1.] \fixture{P1} is no longer in the task's list of registered providers
after the first request, because its stake fell below
\fixture{MINIMUM\_PROVIDER\_STAKE}. \fixture{P2} is no longer registered after
its \fixture{REPEAT\_OFFENSE\_COUNT}-th slash, and its remaining stake is
burned. \fixture{P3}'s reputation is 0 after the first request, \fixture{P3} is
no longer registered, and its remaining stake is burned.
\item[2.] \fixture{P4}'s attempt to unregister is refused with an error message,
and \fixture{P4} stays registered.
\item[3.] \fixture{P4} ($R = 80$) and \fixture{P5} ($R = 50 = R_{\text{exit}}$)
each get all 100 tokens back. \fixture{P6} ($R = 25$) gets
$\frac{25}{50} \times 100 = 50$ tokens back, and the other 50 are burned.
\end{itemize}

\textbf{Test Case Derivation:} \rref{FR_ProviderMinimumStakeUnregistration}, \rref{FR_SlashRepeatedOffenses}, and \rref{FR_ProviderForcedUnregistration} give the three cases where a
provider is removed automatically: stake below the minimum, too many slashes,
and a reputation of 0. \rref{FR_SlashRepeatedOffenses} and \rref{FR_ProviderForcedUnregistration} also require the remaining stake to be
burned. \rref{FR_ProviderWillingUnregistration} does not allow a provider to unregister while it has an active
request. \rref{FR_ProviderUnregistrationStakeReturn} sets how much stake is returned on voluntary unregistration, and
\fixture{P5} sits exactly on the threshold.

\textbf{How test will be performed:} After each request, record each provider's
registration status, stake, and slash count. Record the total burned token
supply and each provider's token balance before and after unregistration, and
assert the expected changes.

\end{enumerate}

\subsubsection{Transparency and Data Handling}

These tests verify that users can see and verify the transactions they
authorize (\rref{FR_TransactionPreview}--\rref{FR_OnChainRecords}) and that a request's input data is protected for its
whole life (\rref{FR_InputAccessRestriction}--\rref{FR_InputDeletion}). They follow a requester who pays for a request and
checks it, and a request's input data from submission to deletion.

\begin{enumerate}

\item{ST-TRANS-1: Requester pays for a request and verifies it\\}

\textbf{Control:} Automatic

\textbf{Initial State:} An authenticated requester is signed in with a test wallet
signer that holds 50 tokens. Task \fixture{Rep-Test-Task} and the providers from
ST-REP-1 are registered.

\textbf{Input:}
\begin{itemize}
\item[1.] Submit an inference request with a payment of 137 tokens.
\item[2.] Add funds so the wallet holds 1000 tokens, then submit the request again
and approve the transaction.
\item[3.] Let the request run to completion, then open the transaction history.
\end{itemize}

\textbf{Output:}
\begin{itemize}
\item[1.] On the first attempt, the system shows an insufficient-funds error and
does not ask the wallet for a signature.
\item[2.] On the second attempt, before the wallet asks for a signature, the
application shows the action (``Submit inference request'') and the amount
(137 tokens).
\item[3.] The transaction status is shown as pending and then confirmed.
\item[4.] The requester's token balance is exactly 137 tokens lower than before
the payment.
\item[5.] The transaction history shows an identifier for the payment. Looking it
up on the public blockchain network returns a transaction that:
\begin{itemize}
\item is signed by the requester's wallet;
\item transfers exactly 137 tokens from the requester's token account to the
request's escrow address.
\end{itemize}
\item[6.] After the request is completed, the blockchain shows:
\begin{itemize}
\item the 137 tokens arriving at the request's escrow address, and then being
transferred from the escrow address to the providers' token accounts, with
transfers that add up to no more than 137 tokens;
\item a stake account for each provider that holds the stake shown on that
provider's dashboard;
\item the final aggregated result stored for the request, equal to the result
shown to the requester;
\item each provider's reputation after the request, equal to the reputation
shown in the application.
\end{itemize}
\end{itemize}

\textbf{Test Case Derivation:} \saref{SA_BalanceCheck} requires a balance check before a signature is
requested. \rref{FR_TransactionAuthorization} requires the requester to sign the payment, \rref{FR_TransactionPreview} requires the action and
amount to be shown before signing, and \rref{FR_TransactionStatus} requires the status to be shown until
it is final. \saref{SA_ChargeEqualsAuthorized} requires the amount charged to equal the amount approved; an
unusual amount (137) is used so that a hard-coded or rounded value would be
caught. \rref{FR_TransactionVerification} requires an identifier that can be looked up on the blockchain, and
\rref{FR_OnChainRecords} lists the records that must be on the blockchain. The escrow is checked by
its transaction history instead of its balance, because the tokens may already
have been paid out by the time it is checked.

\textbf{How test will be performed:} Run the flow in an automated browser test. Pause
the test wallet signer when it receives a signing request and check the
confirmation screen. Record each status shown. Compare balances before and
after. Query the public blockchain network with the transaction identifier, and read the
escrow address's transaction history and the request, stake, and reputation
accounts directly, without going through the application's backend.

\item{ST-DATA-1: Input data from submission to deletion\\}

\textbf{Control:} Automatic

\textbf{Initial State:} Task \fixture{Data-Test-Task} has registered providers
\fixture{P1}, \fixture{P2}, and \fixture{P3}. Another authenticated user
\fixture{U1} is not involved.

\textbf{Input:}
\begin{itemize}
\item[1.] Requester \fixture{R1} submits request \fixture{REQ-A} whose input contains
the marker value \fixture{271828.1828}. \fixture{P1} and \fixture{P2} accept it;
\fixture{P3} does not.
\item[2.] During the commit and reveal phases:
\begin{itemize}
\item \fixture{R1} opens \fixture{REQ-A} in the web client.
\item \fixture{P1}, \fixture{P2}, and \fixture{P3} each call the provider SDK's
method for fetching a request's input and try to decrypt the result with their
own private key.
\item \fixture{U1} and an unauthenticated client call the backend's input-data
endpoint for \fixture{REQ-A} directly.
\end{itemize}
\item[3.] \fixture{REQ-A} runs to completion.
\item[4.] \fixture{R1} submits request \fixture{REQ-B}, which is cancelled because
too few providers accept it.
\end{itemize}

\textbf{Output:}
\begin{itemize}
\item[1.] \fixture{R1} sees \fixture{REQ-A}'s input in the web client.
\fixture{P1} and \fixture{P2} receive the encrypted input and can decrypt it to
the original values. \fixture{P3}'s SDK call is refused, or returns data
\fixture{P3} cannot decrypt. \fixture{U1} and the unauthenticated client are
refused and receive no part of the input.
\item[2.] No transaction or account linked to either request contains the marker
value in readable form.
\item[3.] After each request reaches its final state, its input is no longer in
any storage the system controls, and the web client, the SDK, and the backend
endpoint all return ``not found'' for it, including for \fixture{R1}.
\end{itemize}

\textbf{Test Case Derivation:} \rref{FR_InputAccessRestriction} limits the input to the requester and the providers
that accepted; \fixture{P3} checks that being registered is not enough. \rref{FR_InputNotOnChain}
forbids readable input on the blockchain, and the marker value makes it
possible to search raw on-chain data for it. \rref{FR_InputDeletion} requires deletion after both
completion and cancellation. The test also exercises \rref{FR_RequestInputDistribution} (input given to
accepting providers) and \rref{FR_MinimumAcceptance} (cancellation when too few providers accept).

\textbf{How test will be performed:} Run each access attempt and compare what is
returned with the original input. Search the raw data of every linked
transaction and account for the marker in its common encodings (text, 32-bit
and 64-bit floating point, and the program's fixed-point format). After each
request ends, query the database, file storage, and caches directly and
through the application.

\end{enumerate}

\subsubsection{Safety}

This test verifies the transaction safety requirements that are not already
covered by the tests above (\saref{SA_NoDuplicateSubmission} and \saref{SA_OnChainFundsCheck}--\saref{SA_TransactionSimulation}). \saref{SA_BalanceCheck} and \saref{SA_ChargeEqualsAuthorized}
are covered by ST-TRANS-1, and \saref{SA_RewardValidation} and \saref{SA_ProviderStatusCheck} by ST-REP-1. The test
injects faults using a test build of the backend and a proxy between the
system and the public blockchain network RPC.

\begin{enumerate}

\item{ST-SAFE-1: Requester payments under transaction faults\\}

\textbf{Control:} Automatic, with the retry step also checked manually in the web client

\textbf{Initial State:} A requester is signed in with 1000 tokens. The RPC proxy and
the backend test build can each be set to inject one fault.

\textbf{Input:}
\begin{itemize}
\item[1.] The requester submits an inference request payment through a proxy
that forwards the transaction but drops the response.
\item[2.] The requester submits an inference request payment through a proxy
that holds the transaction until its blockhash has expired.
\item[3.] The requester submits an inference request payment, and the
requester's tokens are moved out of the wallet after the balance check but
before the transaction runs.
\item[4.] The requester submits an inference request payment and signs it with
a different wallet address than the one connected to their account.
\item[5.] The requester submits an inference request payment while the backend
test build changes the transaction's amount to 150 tokens after 100 tokens has
been shown to the user.
\item[6.] After the failure in step 2, the requester presses retry.
\end{itemize}

\textbf{Output:}
\begin{itemize}
\item[1.] Exactly one payment transaction from the requester appears on the
blockchain, the requester's balance goes down by the payment amount once, and
the transaction log shows each status the payment went through.
\item[2.] The payment is shown as failed only after its blockhash has expired,
and no payment from this attempt appears on the blockchain.
\item[3.] The payment transaction fails on the blockchain, no request is
created, and the requester's escrow and request accounts are unchanged.
\item[4.] No transaction is submitted to the blockchain, and the user sees an
error message saying the transaction was signed by the wrong wallet.
\item[5.] The web client does not send the transaction to the wallet for
signing, and the user sees an error message saying the transaction does not
match the amount shown.
\item[6.] The user sees an error message with an option to retry. After pressing
retry, the request is created and exactly one payment for it appears on the
blockchain.
\end{itemize}

\textbf{Test Case Derivation:} Each fault matches one requirement:
\begin{itemize}
\item[1.] \saref{SA_NoDuplicateSubmission} forbids resubmitting before confirming the first transaction was not
processed, and requires status logs.
\item[2.] \saref{SA_ExpiryCheck} requires the system to wait for the validity period to end and check
the status before logging a failure.
\item[3.] \saref{SA_OnChainFundsCheck} requires the on-chain program to check funds when the
transaction runs.
\item[4.] \saref{SA_SignedTransactionsOnly} forbids submitting a transaction that is not signed by the
authorized wallet.
\item[5.] \saref{SA_TransactionSimulation} requires the transaction to be simulated and checked against the
displayed amount before it is signed. The error is introduced by the backend,
and the check is done by the web client, which compares what the user is about
to sign with what is displayed.
\item[6.] \saref{SA_FailureRetry} requires the error to be shown and a retry to be allowed.
\end{itemize}

\textbf{How test will be performed:} Run each fault in turn. Use the proxy to count
submitted transactions and the test wallet signer to count signing requests.
For step 2, compare the time the payment is shown as failed with the block
height at which its blockhash expired, and check that the backend queried the
transaction's status before marking it as failed. For step 4, configure the
test wallet signer to sign with a second test wallet. Count payments from the
requester's wallet on the public blockchain after the whole test and compare the final balance
with the number of successful requests. A tester also runs step 6 by hand in
the web client and records the error message shown.

\end{enumerate}

\subsection{Tests for Nonfunctional Requirements}

This section describes the tests for the non-functional requirements in the
\href{../SRS/SRS.pdf}{SRS} (\nfrref{NFR_ReputationWeightedAggregate}--\nfrref{NFR_NoExtraSoftware} and \saref{SA_ErrorMessageTime}--\saref{SA_DependencyScan}). As with the
functional tests, each test is a larger activity that checks several related
requirements at once: a large simulation of many requests, a usability study, a
security and privacy audit, and a set of release checks. Some tests produce
measurements, tables, or graphs rather than a single pass or fail result.
Values that have not been decided yet are written as symbolic constants and
are listed in the Symbolic Parameters appendix.

\subsubsection{Accuracy, Reliability, and Scalability}

\begin{enumerate}

\item{NFR-SIM-1: Large-scale request simulation\\}

\textbf{Control:} Automatic

\textbf{Initial State:} The system runs on a local validator for the public blockchain network with a simulation
harness that controls mock providers and can inject faults. A separate
reference implementation of the Appendix A aggregation algorithm is written
in TypeScript by a team member who did not write the system's version.

\textbf{Input:}
\begin{itemize}
\item[1.] Run \fixture{NUM\_SIMULATED\_REQUESTS} requests with random predictions
and reputation scores, including values at the edges of their declared ranges
(reputation 0 and 100, the largest and smallest allowed predictions and token
amounts) and the worked examples from the SRS.
\item[2.] Mix in failure scenarios: too few providers accept, too few valid
predictions, providers that do not commit or reveal, mismatched commitments, invalid revealed predictions, dropped or
delayed RPC responses, and a backend restart during the commit and reveal phases.
\item[3.] Run the requests at 1, 5, 10, 20, and \fixture{MAX\_CONCURRENT\_REQUESTS}
at the same time. Mock providers reply immediately, so only the system's own
processing time is measured.
\item[4.] During each commit phase, try to read any individual prediction from on-chain and backend data as
another provider, as the requester, and from the raw on-chain data; include the backend database and logs.
\item[5.] Generate a salt for each mock provider. Inspect the SDK-generated salt length and persistence before and after a simulated restart, then use the same salt for reveal.
\end{itemize}

\textbf{Output:}
\begin{itemize}
\item[1.] Every aggregated result equals the reference implementation's result.
The test reports the number of mismatches (expected: 0).
\item[2.] No calculation overflows. Any input that would overflow causes the
transaction to fail with no change to on-chain state.
\item[3.] Every request reaches a final state before its final deadline, and its
escrow is empty afterwards.
\item[4.] No individual prediction can be read from on-chain or backend data before the commit phase ends.
\item[5.] Each salt contains at least 256 bits, is generated by a cryptographically secure random generator, and remains available in the SDK after restart until reveal completes.
\item[5.] A table and graph of the median and 95th-percentile processing time at
each concurrency level. The test passes if the median at
\fixture{MAX\_CONCURRENT\_REQUESTS} is no more than
\fixture{PERFORMANCE\_DEGRADATION\_TOLERANCE} higher than for a single request.
\end{itemize}

\textbf{Test Case Derivation:} \nfrref{NFR_ReputationWeightedAggregate} requires simulation tests to show that the results
match the Appendix A algorithm. \nfrref{NFR_AggregationArithmeticErrors} forbids overflow and requires an
overflowing transaction to leave no change. \nfrref{NFR_FinalState} requires every request to
reach a final state and settle its escrow before the final deadline. \nfrref{NFR_PredictionsHidden}
requires predictions to stay hidden until the commit phase ends. \nfrref{NFR_CommitSalt} requires a cryptographically secure 256-bit salt to persist until reveal. \nfrref{NFR_ConcurrentRequests} requires
concurrent requests without a drop in performance.

\textbf{How test will be performed:} The harness runs the requests and then reads each
request's status, result, and escrow from the blockchain. It compares each
result with the reference implementation and logs the inputs of any mismatch
so they can be added as a unit test. It checks that the tokens escrowed at the
start equal the tokens paid out, returned, slashed, and burned. Each
concurrency level is run 3 times, and the timings come from the system's logs.

\end{enumerate}

\subsubsection{Usability}

\begin{enumerate}

\item{NFR-USE-1: Usability study with new users\\}

\textbf{Control:} Manual, with timing checks automated

\textbf{Initial State:} The web application is deployed on a test environment
connected to the public blockchain network. 5 to 8 participants who use a web browser but have
never used a blockchain wallet or built a machine learning model are recruited.

\textbf{Input:} Each participant gets a short description of DAIIM, but no
instructions on how to use it, and completes these tasks while thinking out
loud:
\begin{itemize}
\item[1.] Sign in by creating an embedded wallet with an email address.
\item[2.] Find the documentation and the list of available tasks.
\item[3.] Submit an inference request for an existing task.
\item[4.] Find the result of the request and the payment for it.
\item[5.] Sign out.
\end{itemize}
During task 3, the test build forces one error (a failed transaction). The
participant then fills out the survey in the Usability Survey Questions
appendix.

\textbf{Output:}
\begin{itemize}
\item[1.] At least \fixture{USABILITY\_COMPLETION\_RATE} of participants complete
every task without help, including creating a wallet with no Web3 knowledge.
\item[2.] The median time to finish tasks 1 to 3 is 5 minutes or less.
\item[3.] Every feature can be reached within 2 clicks of the home page.
\item[4.] Every error shown has a name, a description, and a suggested fix, and
appears within 2 seconds of the failure being detected.
\item[5.] A progress indicator is shown during every operation longer than
\fixture{LONG\_OPERATION\_THRESHOLD}.
\item[6.] A plain-language confirmation is shown after every transaction.
\item[7.] The survey results are summarized in a table and bar chart.
\end{itemize}

\textbf{Test Case Derivation:} \nfrref{NFR_Learnability} requires a new user to learn the system within 5
minutes, and \nfrref{NFR_EmbeddedWalletAccess} requires them to create an embedded wallet without Web3
knowledge. \nfrref{NFR_TwoClickAccess} requires every feature within 2 clicks. \nfrref{NFR_ErrorVisibility} requires errors to
have a name, description, and fix, and \saref{SA_ErrorMessageTime} requires them within 2 seconds.
\nfrref{NFR_ProgressStatus} requires progress to be shown for long operations, and \nfrref{NFR_TransactionConfirmation} requires
plain-language confirmations.

\textbf{How test will be performed:} A team member observes each session, times each
task, records clicks, and only helps if the participant is stuck for more than
3 minutes (which counts as not completing the task). A team member also
counts the clicks to each feature from the home page. Error timings and
progress indicators are checked by an automated browser test that repeats the
same tasks with forced errors and delays. One study is held after the Rev 0
demo and a second after changes are made in response to it.

\end{enumerate}

\subsubsection{Security, Privacy, and Safety}

\begin{enumerate}

\item{NFR-SEC-1: Security and privacy audit\\}

\textbf{Control:} Manual, with automated scans

\textbf{Initial State:} The system is deployed in its test environment. A request is in
progress, so its input data is stored. Test providers have consented to
showing different sets of profile information.

\textbf{Input:}
\begin{itemize}
\item[1.] Run a full request with an extension wallet and with an embedded wallet,
capturing network traffic and backend logs.
\item[2.] Read the raw contents of the database and file storage.
\item[3.] Scan every endpoint's TLS setup, connect over plain HTTP, and point the
backend at RPC and storage endpoints that use a self-signed certificate.
\item[4.] Visit every public page without signing in.

  \textbf{Aidan:} The main pain point was that some parts of the SRS were not
  yet specific enough to test. For example, several constants such as
  \fixture{SLASH\_FRACTION} and \fixture{MAX\_REPUTATION\_PENALTY} are still

  wrote down the assumption made in the reward test so the team can confirm it

  small test for almost every requirement, which made my sections very long

  VnV plan from another capstone group, I realized that system tests should
  follow larger, realistic scenarios, like a requester paying for a request and
  checking it on the blockchain, or a group of providers misbehaving during one
  request. I rewrote my sections so that each test covers about five to seven

  lost in the rewrite, I checked that every requirement in my sections was
  still named in at least one test. We also added the question of how detailed

  document, it became difficult to keep track of which fixtures were being used
  in which tests, and what each one represented. We decided, to resolve this, to avoid

  each time.

  appendix. In hindsight, deciding on this convention before writing the tests
