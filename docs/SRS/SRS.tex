\subsection{Purpose}

DAIIM (Decentralized Artificial Intelligence Inference Marketplace) exists to reduce reliance on the small number of large organizations that currently provide most AI inference. It serves two groups of people.

For people who need machine learning predictions, DAIIM provides a way to obtain inferences for a task they define without trusting a single centralized provider. Each inference request is answered by multiple independent providers, and their predictions are combined into one consensus result. Because no single provider controls the outcome, the result is more reliable, harder to censor or manipulate, and not dependent on any one point of failure.

For people who build machine learning models, DAIIM provides an open marketplace where they can sell predictions from their models and earn money for accurate results. This gives independent providers a way to compete with large organizations and a reason to keep improving their models.

\subsection{Scope}

DAIIM allows task requesters to obtain reliable inferences by combining predictions from multiple independent inference providers.

The inputs to the system consist of task definitions, inference requests, and network participation.
Task definitions are specifications of a problem to be solved via machine learning, including the expected input and output types.
Inference requests ask the network to perform inference for a given task and include
input data or some specification of where to find the input data.
Network participation includes machine learning
predictions for individual inference requests that are supplied to the network by an individual.
The system outputs aggregated inference results and maintains information about the network.
The aggregated inference results include the final prediction for a given inference request, as well as information about the quality of the prediction.

The expected benefits are reduced reliance on centralized AI providers, improved reliability of inferences through redundant predictions from
independent providers, and incentives for providers to improve the quality, performance, availability, and cost-effectiveness of their models.

The following are outside the scope of DAIIM:
\begin{itemize}
    \item Inference tasks whose output is not a single numeric value, such as predicting a category label. Support for additional model types is a stretch goal.
    \item Inference on private or sensitive data within Trusted Execution Environments (TEEs). This is a stretch goal.
    \item DAIIM doesn't train models. It just uses model providers' existing models to make predictions for inference requests.
    \item Using a custom blockchain. DAIIM will use Solana, an existing public blockchain.
\end{itemize}

\subsection{Stakeholders} \label{sec_Stakeholders}

\subsubsection*{Primary Stakeholders}

Primary stakeholders interact with DAIIM directly.

\begin{itemize}
    \item \textbf{Task requesters} \newline
    Task requesters are people who are requesting inferences to be made for a given task, using their own input data.
    These people value consensus and reliability: they want a prediction that combines the results of multiple independent models, rather than relying on a single model that may be wrong, biased, or unavailable.
    For example, emergency management agencies would make requests to predict river levels or wildfire risk, where a single incorrect forecast can leave a community unprepared.
    Similarly, decentralized finance platforms could make requests to predict stock prices, where relying on a single source of predictions creates a risk of error or manipulation.
    Because input data is shared with inference providers, task requesters are expected to submit data that is not sensitive.

    \item \textbf{Inference providers} \newline
    Inference providers are people with computing resources and models, and want to monetize their regression models.
    These people usually have specialized or powerful models that can be used to make predictions for a given task.
\end{itemize}

\subsubsection*{Secondary Stakeholders}

Secondary stakeholders do not use DAIIM directly, but are affected by the inferences it produces or by how it handles data.

\begin{itemize}
    \item \textbf{Beneficiaries of machine learning inference} \newline
    Beneficiaries are people and organizations, such as laboratories, that rely on the results of machine learning inference without requesting inferences themselves.
    For example, a laboratory may make decisions based on biomarker predictions that a healthcare researcher obtained through DAIIM.
    These people benefit from inferences that are reliable and not controlled by a single provider.

    \item \textbf{Regulatory bodies} \newline
    Regulatory bodies are organizations that oversee machine learning inference and data privacy.
    They want to ensure that personal information and sensitive data handled by DAIIM, such as inference inputs and training data, is only accessible to the parties that need it, is encrypted, and is not retained longer than necessary to fulfill an inference request.
\end{itemize}

\section{System Overview}

This section provides general information about the system.  It identifies the
problem, the vision, and the interfaces between the system and its environment.
This section also describes user characteristics and lists the system
constraints.

\subsection{Problem Statement}

AI inference services often rely on centralized providers, which can create single points of failure and leave users dependent on a single service for their results. Users may also have limited visibility into how results are obtained, how reliable they are, and whether the service provider is operating as expected.
These limitations raise concerns about service availability, trust, and the ability to assess the quality of inference results. Relying on a single provider also limits opportunities for independent providers to contribute their inference capabilities to a shared marketplace.
DAIIM addresses the need for an approach to AI inference that supports greater reliability, accountability, and participation. The underlying problem is how to provide users with confidence in inference results while allowing multiple providers to participate and be evaluated fairly, without requiring users to rely entirely on one centralized service.


\subsection{Product Vision}


DAIIM aims to make AI inference more reliable, transparent, and accessible by connecting users who need predictions with independent providers who can supply them. By combining predictions from multiple providers and making relevant performance and transaction information available, the marketplace seeks to build trust in inference results while creating opportunities for providers to offer their services.
The system's goals are to:
\begin{itemize}
\item Improve the reliability of inference results by combining predictions from multiple independent providers, assessing the quality of their contributions, and reducing dependence on any single provider.
\item Create a fair and accountable marketplace in which providers can build reputations and receive compensation based on their performance.
\item Make marketplace activities transparent by allowing users to inspect aggregated results, relevant provider performance information, and records of transactions and payments.
\item Make AI inference accessible to users without requiring prior knowledge of AI or Web3 technologies, while giving inference providers a way to offer their services and earn compensation for their contributions.
\end{itemize}

\subsubsection{Responsibilities}
\begin{itemize}

\item \textbf{Task Requester Responsibilities:}
\begin{itemize}
    \item Define the inference task by specifying the problem to be solved, the expected input and output formats, and other required task settings.
    \item Submit requests for predictions using an existing task definition and input data that conforms to the task's requirements.
    \item Specify the amount of tokens offered for an inference request and authorize the associated payment transaction.
    \item Receive the final aggregated prediction, information about the range of provider predictions, the number of providers that submitted predictions, and the request status.
    \item View the status and results of previously submitted inference requests.
\end{itemize}

\item \textbf{Inference Provider Responsibilities:}
\begin{itemize}
    \item Register to provide predictions for an inference task by staking the required amount of tokens.
    \item Receive information about available requests for tasks they are registered for, including the task requirements, input data, proposed payment, and relevant timing information.
    \item Accept or decline participation in available inference requests.
    \item Submit a prediction that conforms to the task's required output format for each request they accept.
    \item Access information about their reputation, staked tokens, and rewards earned for each registered task.
\end{itemize}

\item \textbf{Blockchain Network Responsibilities:}
\begin{itemize}
    \item Process marketplace transactions authorized by users, including transactions related to request payments, provider stakes, and provider compensation.
    \item Record marketplace information designated for on-chain storage, including request payments, provider stakes, aggregated results, reputation updates, and reward distributions.
    \item Make transaction status and transaction records available for verification.
\end{itemize}


\end{itemize}


\subsubsection{Operating Context and Safety Significance}
DAIIM is intended to be used as a web-based marketplace for requesting and evaluating AI inference results from multiple independent providers. Users submit inference requests through the system and receive aggregated predictions along with information about the contributing providers and the results they submitted. Blockchain technology is a required component of DAIIM, supporting transparent and verifiable records of marketplace activities, including provider stakes, payments, aggregated results, and reward distributions.
DAIIM may be used in applications where reliable predictions are important, such as wildfire detection, where inaccurate or unavailable results could delay the identification of potential hazards. By combining predictions from multiple providers, the system aims to reduce dependence on any single provider and improve the reliability and availability of inference results. However, using multiple providers does not guarantee a correct result, as providers may submit inaccurate predictions or share similar sources of error.
Although DAIIM does not directly control physical systems or make decisions on behalf of its users, its results may inform safety-critical applications where incorrect predictions could have serious consequences. Users are therefore responsible for validating aggregated results and determining whether they are sufficiently reliable for their intended use. The system must also account for risks such as provider collusion, unavailable providers, failed transactions, and incorrect aggregation or reputation calculations, as these may affect the trustworthiness of its results and marketplace operations.



\subsection{User Characteristics} \label{SecUserCharacteristics}
DAIIM is intended to support users with varying levels of technical expertise.
\begin{itemize}
\item \textbf{Task Requesters:} Task requesters should have a basic understanding of the inference task they wish to perform and be able to provide the required input data. They should be able to use a modern web browser and interpret the inference results presented by the system. They are not expected to understand the internal aggregation, reputation, or reward algorithms.
\item \textbf{Inference Providers:} Inference providers should have sufficient technical knowledge and computational resources to execute the inference tasks they accept. They should understand the requirements for submitting predictions in a format supported by the marketplace.


\end{itemize}
The user interface should minimize the technical knowledge required to submit requests and interpret results, while provider participation may require greater technical expertise.



\subsection{System Constraints}

\begin{itemize}
\item \textbf{Web3 browser compatibility:} The user-facing application must be accessed through a web browser that supports the Web3 wallet extensions required to authenticate users and authorize blockchain transactions.
\item \textbf{Inference type and data compatibility:} The system is restricted to regression-based inference for the initial project. Inference requests must provide input data in a supported format, and provider predictions must conform to the expected numerical output format so that results can be validated and aggregated consistently.
\item \textbf{Blockchain integration:} Marketplace operations that require on-chain execution must be compatible with the blockchain network selected for the project. The system must account for possible transaction delays or failures.
\end{itemize}

\section{Stakeholder Requirements}

This section lists the stakeholder requirements for DAIIM, grouped by the stakeholders described in Section~\ref{sec_Stakeholders}. These requirements are technology-independent and are stated from the point of view of the stakeholders.

\subsubsection*{Task Requesters}

\noindent \begin{itemize}

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_DefineTask}] Task requesters shall be able to define their own machine learning task, including the type of input the task takes and the type of output it produces.

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_RequestInference}] Task requesters shall be able to submit an inference request for a defined task and receive a result for that request.

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_ReliableInference}] Task requesters shall receive inference results that are reliable. Each result shall be based on predictions from multiple independent inference providers, so that no single faulty or dishonest provider can determine the result.

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_ResilientService}] Task requesters shall receive results for their inference requests even when some inference providers are unavailable.

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_ResultQuality}] Task requesters shall receive information about the quality of each inference result, so that they can judge how much to trust it.

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_NoCentralAuthority}] Task requesters shall be able to obtain inferences without relying on a single organization to coordinate the request, supply the prediction, or control the result.

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_Transparency}] Task requesters shall be able to see the actions and payments they authorize, and verify that those actions and payments were carried out.

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_EaseOfUse}] Task requesters shall be able to define tasks, submit inference requests, and receive results without knowledge of decentralized systems or their underlying infrastructure.

\end{itemize}

\subsubsection*{Inference Providers}

\noindent \begin{itemize}

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_ProviderParticipation}] Inference providers shall be able to offer predictions from their own models for tasks defined by task requesters.

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_ProviderProfit}] Inference providers shall be able to earn a profit by supplying accurate predictions to the network.

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_RewardAccuracy}] Inference providers shall be rewarded according to the accuracy of their predictions, so that supplying honest, accurate predictions is more profitable than supplying dishonest or careless ones.

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_AutomaticPayment}] Inference providers shall receive payment for their predictions without manual intervention from the task requester or any third party.

\end{itemize}

\subsubsection*{Secondary Stakeholders}

\noindent \begin{itemize}

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_DataPrivacy}] Personal information and sensitive data handled by DAIIM, such as inference inputs and training data, shall only be accessible to the parties that need it to fulfill an inference request.

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_DataProtection}] Personal information and sensitive data handled by DAIIM shall be protected from unauthorized access while it is transferred and while it is stored.

\item[SR\refstepcounter{srnum}\thesrnum \label{SR_DataRetention}] Personal information and sensitive data handled by DAIIM shall not be retained longer than necessary to fulfill the inference request it belongs to.

\end{itemize}

\section{User Personas}

\subsection{Persona 1: Emergency Management Coordinator (Task Requester)}
\begin{itemize}
\item Name: Priya Nair
\item Description: Priya is 41 and coordinates emergency management for a mid-sized town on a flood-prone river, in a region that also has an annual wildfire season. She decides when to issue flood warnings and evacuation orders, and when to pre-position firefighting resources. She currently relies on a single forecasting service, and has to justify every decision to the town council.
\item Goals: Receive river-level forecasts 24 to 48 hours ahead, and wildfire risk estimates during fire season, that combine predictions from multiple independent sources. See how much the sources agree, so she knows how much to trust each forecast. Keep costs predictable and within the town's budget.
\item Frustrations: Her current service is a black box: it gives one number with no indication of confidence, and she has no alternative when it is wrong or unavailable. A missed flood forecast the previous spring left the town unprepared. She has no interest in learning about cryptocurrency or managing digital wallets.
\item Technical Ability: Comfortable with spreadsheets, web dashboards, and mapping tools. No programming experience and no experience with blockchain or Web3 applications.
\end{itemize}

\subsection{Persona 2: Independent Stock Forecaster (Inference Provider)}
\begin{itemize}
\item Name: Daniel Okafor
\item Description: Daniel is 29 and works as a software developer. In his spare time he builds machine learning models that predict next-day stock prices from historical market data. His models perform well in backtests, but he has no way to earn money from them other than trading with his own savings.
\item Goals: Earn a steady side income by supplying predictions from his models. Get paid automatically and promptly for good predictions. Build a visible track record that shows his models are reliable. Keep the cost of submitting each prediction low enough that participating is worthwhile.
\item Frustrations: Selling predictions usually requires connections at a fund. Trading his own money exposes him to large losses. Prediction platforms he has tried were unclear about how payouts were calculated.
\item Technical Ability: Strong Python programmer who regularly uses machine learning libraries. Owns a cryptocurrency wallet and has used decentralized finance applications.
\end{itemize}

\subsection{Persona 3: Hydrology Researcher (Inference Provider)}
\begin{itemize}
\item Name: Dr. Elena Varga
\item Description: Elena is 34 and is a postdoctoral researcher in hydrology. She specializes in forecasting streamflow in mountain rivers fed by melting snow, where standard forecasting models often perform poorly during the spring melt. Her models currently only appear in academic papers.
\item Goals: Earn supplementary income from her expertise by supplying predictions for tasks in her field, such as river-level and streamflow forecasts. Build a reputation for her models outside academia. See her research help communities prepare for floods.
\item Frustrations: Consulting contracts are slow to arrange and rarely available to early-career researchers. Her models are most valuable during unusual events, when they disagree with standard models, and she worries about being penalized for disagreeing with the majority even when she is right.
\item Technical Ability: Expert in statistical modeling, with strong Python and R skills. Has never used a cryptocurrency wallet or a blockchain application.
\end{itemize}

\subsection{\ucref{UC_SignIn}: Sign in to the web application.}

\textbf{Primary Actor}
User (requester or provider)

\textbf{Preconditions}
\begin{itemize}
\item User has an account that is supported by MetaMask authentication (Google, Twitter, email, SMS, etc.).
\end{itemize}

\textbf{Main Success Scenario}
\begin{enumerate}
\item User opens the DAIIM web application in a browser.
\item User clicks the "Sign in" button.
\item System displays a list of supported sign-in methods.
\item User selects their preferred sign-in method (ie. Google, Twitter, email, SMS, existing supported wallet, etc.).
\item User signs in with MetaMask Embedded Wallet infrastructure.
\item System retrieves the JSON Web Token (JWT) and verifies the public key linked to the user's wallet.
\item System authenticates the user and displays their profile linked with their wallet.

\end{enumerate}

\textbf{Alternative Flows}
\begin{itemize}
\item 5a. User cancels the sign-in process: System cancels sign-in and redirects user to the public page.
\item 5b. User fails to input correct credentials: System displays an error message and prompts the user to try signing in again or choose another account.
\item 6a. System fails to verify the JWT or public key: System displays an error message and prompts the user to try signing in again.
\end{itemize}

\textbf{Postconditions}
\begin{itemize}
\item The requester is signed in to the DAIIM web application and can access their profile and other features of the application.
\end{itemize}

\refstepcounter{ucnum} \label{UC_ProviderRegistration}
\subsection{\ucref{UC_ProviderRegistration}: Register as an inference provider for a task}

\textbf{Primary Actor}
Provider

\textbf{Preconditions}
\begin{itemize}
\item Provider has an authenticated wallet and a model that can perform inference for a task.
\item The task exists.
\end{itemize}

\textbf{Main Success Scenario}
\begin{enumerate}
\item Provider fills out the provider template and connects via the SDK.
\item System verifies that the provider is properly connected.
\item System verifies that the provider is not already registered for the task.
\item System verifies that the provider's wallet holds at least the task's minimum stake.
\item System requests that the provider consent to the staking and reputation conditions, the public display of the provider's name and reputation, the privacy agreement, and informs the provider that on-chain data is permanent.
\item Provider consents.
\item System requests the stake from the provider's wallet, explaining the action and the amount required.
\item Provider confirms and signs the stake transaction.
\item System verifies that the stake meets the task's minimum, locks it in escrow, assigns the base reputation for the task, and adds the provider to the list of registered providers for the task.
\item System displays the transaction status until it is confirmed and returns the transaction identifier to the provider.
\end{enumerate}

\textbf{Alternative Flows}
\begin{itemize}
\item 1a. The provider template is incomplete or invalid: the SDK rejects it and names the missing or invalid field.
\item 2a. The provider is not connected, the session has expired, or the wallet is on the wrong cluster: the system displays an error with the cause and a suggested fix, and no funds move.
\item 3a. The provider is already registered for the task: the system displays an error and the provider's current registration, and the use case ends.
\item 3b. The provider was registered before and unregistered: registration proceeds, and the reputation starts at the base reputation regardless of the earlier score.
\item 4a. The wallet balance is below the minimum stake, or there is not enough SOL for the network fee: the system displays an error showing the shortfall for each, and the use case ends.
\item 6a. The provider does not consent: the system explains that registration requires consent, nothing is signed or recorded, and the use case ends. The provider may start again.
\item 8a. The provider declines to sign the stake transaction: no stake is locked, the provider is not registered, and the use case ends. The provider may start again.
\item 9a. The system detects that the stake does not meet the task's minimum: the transaction is rejected, and no stake is locked.
\item 9b. The network is unavailable or the transaction fails: no stake is locked and the provider is not registered. The system displays an error stating that no funds moved, and a retry does not create a duplicate registration.
\end{itemize}

\textbf{Postconditions}
\begin{itemize}
\item The task's minimum stake is locked in escrow.
\item The provider is registered for the task with the base reputation, appears in the task's list of registered providers, and can accept inference requests and submit predictions for it.
\item The registration, stake, and provider's consent are recorded and the provider has the transaction identifier.
\end{itemize}

\refstepcounter{ucnum} \label{UC_UpdateReputation}
\subsection{\ucref{UC_UpdateReputation}: Update and maintain provider reputation}

\textbf{Primary Actor}
System

\textbf{Preconditions}
\begin{itemize}
\item All required predictions have been submitted and verified, and the final inference result has been calculated.
\end{itemize}

\textbf{Main Success Scenario}
\begin{enumerate}
\item System retrieves valid submitted predictions from providers whose reputation score at the end of the prediction phase, before any reputation updates for that request, was non-zero, and retrieves the final inference result.
\item System calculates the accuracy of each provider's prediction by comparing it to the final inference result produced using the weighted-median algorithm in Appendix~A (\nameref{App_WeightedMedian}).
\item System updates the reputation score of each provider whose valid prediction was included in the aggregate, based on the accuracy of their prediction and using the reputation update rules in \rref{FR_ReputationIncrease}, \rref{FR_ReputationUnchanged}, and \rref{FR_ReputationDecrease}.
\item System stores the updated reputation scores in the provider's profile.
\end{enumerate}

\item 2a. System encounters an error during the accuracy calculation or reputation update process: System retries the operation.
\item 3a. System calculates a reputation score that is below the minimum threshold for the task: System informs the provider that their reputation score has fallen below the minimum threshold and the consequences, unregisters them from the task, and burns their staked tokens.
\item 3b. Provider has been slashed for at least REPEAT\_OFFENSE\_COUNT of the last REPEAT\_OFFENSE\_WINDOW: Provider is notified of offense and concequences. Provider is unregistered from the task and tokens are burned.
\end{itemize}

\textbf{Postconditions}
\begin{itemize}
\item Provider reputations are updated based on the accuracy of their predictions, and any providers with reputations below the minimum threshold are unregistered from the task.
\end{itemize}

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_TaskAcceptancePeriod}:] Each inference task definition shall specify the length of the acceptance period for the task's inference requests. The acceptance period for each request shall end this length of time after the request is broadcast.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_TaskMaxPredictionTime}:] Each inference task definition shall specify the maximum prediction time for the task's inference requests, measured from the end of the acceptance period.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_TaskBrowsing}:] The system shall allow all users to browse existing inference tasks and view each task's definition, required minimum provider stake, and number of registered providers.

\subsection{Provider Registration and Staking}

\noindent \begin{itemize}

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_InferenceTaskRegistration}:] The system shall allow authenticated users to register as inference providers for an inference task by staking the required minimum amount of tokens.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_InferenceTaskRegistrationStaking}:] When a provider registers for an inference task, the system shall lock the required minimum stake for that task in escrow. The system shall return the provider's stake when the applicable conditions for releasing it are met.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_ProviderWillingUnregistration}:] The system shall allow registered inference providers to unregister from an inference task, provided they have not accepted any active inference requests for that task. Upon unregistration, the provider shall be removed from the list of registered providers for the task, and their remaining staked tokens shall be returned to their token account. Upon re-registering for an inference task, the provider shall start with the baseline reputation score for that task, regardless of their previous reputation score.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_ProviderDashboard}:] The system shall allow inference providers to view their reputation score, staked tokens, and rewards earned for each inference task they are registered for.

\end{itemize}

\subsection{Inference Requests}

\noindent \begin{itemize}

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_RequestSubmission}:] The system shall allow authenticated users to submit inference requests for an existing inference task. Each request shall include input data that conforms to the task's input schema.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_RequestValidation}:] The system shall reject inference requests whose input data does not conform to the task's input schema.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_RequestPayment}:] When submitting an inference request, the system shall require the requester to choose a payment amount in tokens greater than the minimum and prompt them to authorize, through their connected wallet, a transaction transferring that amount of tokens into escrow.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_RequestBroadcast}:] After an inference request is submitted, the system shall broadcast its task definition, proposed payment amount, acceptance-period expiry time, and maximum prediction time to all providers registered for the task.

\end{itemize}

\subsection{Provider Acceptance and Predictions}

\noindent \begin{itemize}

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_AcceptancePeriodStart}:] Upon broadcast of an inference request, the system shall automatically begin the acceptance period, during which providers registered for the task may accept or decline participation.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_AcceptancePeriodEnd}:] At the specified expiry time, the system shall end the acceptance period. All registered providers that have not accepted the request will be treated as non-participating. Inference request acceptances from inference providers outside of the acceptance period will not be considered.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_MinimumAcceptance}:] If fewer than the task's minimum number of participating providers have accepted an inference request when the acceptance period ends, the system shall cancel the request and return the requester's escrowed payment.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_RequestInputDistribution}:] The system shall make the request's input data, or information needed to access it, available to all providers that accepted the request during the acceptance period.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_PredictionPhaseStart}:] Upon expiration of the acceptance period, the system shall begin collecting inferences from the set of providers that accepted the request. Predictions returned from inference providers that are not participating will be rejected.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_PredictionSubmission}:] The system shall allow each provider that accepted an inference request to submit a prediction for that request during the prediction phase.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_OnePredictionPerProvider}:] The system shall accept at most one prediction from each provider for a given inference request.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_PredictionValidation}:] The system shall reject predictions that do not conform to the task's output schema.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_PredictionPhaseEnd}:] The system shall end the prediction phase when it has received a prediction from every provider that accepted the request or when the maximum prediction time has elapsed, whichever occurs first. The system shall not accept predictions after the phase has ended.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_MinimumPredictions}:] When the prediction phase ends, the system shall count the providers who submitted a valid prediction and whose reputation score is non-zero. If fewer than the task's minimum number of providers meet these conditions, the system shall cancel the request and return the requester's escrowed payment.

\end{itemize}

\subsection{Aggregation and Results}

\noindent \begin{itemize}

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_PredictionAggregation}:] The system shall aggregate only valid submitted predictions from providers whose reputation score at the end of the prediction phase, before any reputation updates for that request, is non-zero. For each included prediction, its weight shall be that reputation score divided by the sum of the reputation scores of all included providers. The system shall calculate the final numerical result using the weighted-median algorithm specified in Appendix~A (\nameref{App_WeightedMedian}).

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_FinalResultDelivery}:] The system shall return the final aggregated result, time elapsed since submitting the request, and the number of provider predictions included in the aggregation to the user that submitted the inference request.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_ResultSpread}:] The system shall return, with each final aggregated result, the minimum and maximum of the predictions included in the aggregation.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_RequestHistory}:] The system shall allow requesters to view the status of each inference request they have submitted and, once available, its final aggregated result.

\end{itemize}

\subsection{Reputation and Rewards}

\noindent \begin{itemize}

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_UpdateProviderReputations}:] After the final aggregated result for an inference request is computed, the system shall update the reputation score of each provider whose valid prediction was included in the aggregate under \rref{FR_PredictionAggregation}. For each such provider $i$, the system shall compute $d_i$, the absolute difference between the provider's prediction and the final aggregated result, and $\bar{d}$, the average of $d_j$ over all providers whose valid predictions were included in the aggregate.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_ReputationRange}:] The system shall maintain each provider's reputation score within the inclusive range $[0,100]$

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_ReputationIncrease}:] The system shall increase the reputation score of a provider whose distance $d_i$ is less than or equal to the average distance $\bar{d}$.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_ReputationUnchanged}:] The system shall leave unchanged the reputation score of a provider whose distance $d_i$ is greater than $\bar{d}$ but less than or equal to $\bar{d} + T$, where $T$ is the task's reputation tolerance.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_ReputationDecrease}:] The system shall decrease the reputation score of a provider whose distance $d_i$ is greater than $\bar{d} + T$, where $T$ is the task's reputation tolerance.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_ReputationPenaltyCap}:] The system shall limit the reputation decrease a provider receives for a single inference request to at most MAX\_REPUTATION\_PENALTY, regardless of how far the provider's prediction is from the final aggregated result.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_DistributeRewards}:] The system shall distribute the inference request's reward among all providers whose predictions contributed to the final aggregated result and whose reputation did not decrease as a result of the request, in proportion to each provider's reputation score. 
\end{itemize}

\subsection{Penalties}

\noindent \begin{itemize}

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_InferenceProviderSlashing}:] The system shall slash a provider's stake only under the conditions specified in \rref{FR_SlashInvalidPrediction} and \rref{FR_SlashNoShow}, and shall burn a provider's remaining stake only under the conditions specified in \rref{FR_SlashRepeatedOffenses} and \rref{FR_ProviderForcedUnregistration}.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_SlashInvalidPrediction}:] When the system rejects a provider's prediction under \rref{FR_PredictionValidation}, the system shall slash SLASH\_FRACTION of the provider's stake for the task and decrease the provider's reputation score.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_SlashNoShow}:] When a provider that accepted an inference request has not submitted any prediction for the request by the end of the prediction phase, the system shall slash SLASH\_FRACTION of the provider's stake for the task and decrease the provider's reputation score.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_ProviderMinimumStakeUnregistration}:] Whenever a provider's stake for an inference task falls below MINIMUM\_PROVIDER\_STAKE, the system shall automatically unregister the provider from that task.

\item[FR\refstepcounter{reqnum}\thereqnum \label{FR_SlashRepeatedOffenses}:] When a provider has been slashed for at least REPEAT\_OFFENSE\_COUNT of the last REPEAT\_OFFENSE\_WINDOW inference requests they accepted for a task, the system shall unregister the provider from the task and burn their remaining stake for the task.

 \item[FR\refstepcounter{reqnum}\thereqnum \label{FR_ProviderForcedUnregistration}:] The system shall automatically unregister any inference provider whose reputation score reaches $0$. Upon unregistering, the system shall burn the provider's remaining staked tokens for the associated inference task.
\end{itemize}

\subsection{Privacy and Data Retention}

DAIIM will use a semi-private approach for inference request input data. Inputs
will be encrypted and made accessible only to the requester and providers that
accept the request. By submitting a request, the requester consents to the
input being shared with those providers and should not submit data they
consider fully private or confidential. Input data will be stored only as long
as needed to fulfill the request and will be deleted from storage controlled by
the system once the request is completed or cancelled, following established
data-minimization and retention practices. The system will not store readable
input data on the blockchain. DAIIM's handling of personal data must follow
applicable privacy and data-protection laws for its deployment and users; the
specific obligations will depend on the relevant jurisdictions.

Other data, including wallet addresses, provider reputations, task definitions,
request status and results, and token-economics records, will be collected and
retained only as needed to operate the marketplace, provide its features, and
meet applicable legal obligations. Information needed for public marketplace
and blockchain functions may be visible to other users; users should be
informed that blockchain records may be permanent and cannot necessarily be
deleted. Data stored off-chain will be protected against unauthorized access
and encrypted in transit and at rest where appropriate.

\section{AI and Machine Learning Requirements}

This section describes how DAIIM supports machine-learning inference, evaluates
prediction quality, and communicates the limitations of its results. The
project scope focuses on regression tasks: each task defines its input and
output schemas, providers submit numerical predictions, and the system combines
those predictions into a reputation-weighted result.

\subsection{Evaluation Metrics}

For regression tasks with available ground-truth values, DAIIM will evaluate
predictions using mean absolute error (MAE), calculated as the arithmetic mean
of the absolute differences between predicted and ground-truth values across
evaluated requests:
\[
\mathrm{MAE} = \frac{1}{n}\sum_{i=1}^{n} \lvert \hat{y}_i - y_i \rvert,
\]
where $n$ is the number of evaluated requests, $\hat{y}_i$ is a predicted
value, and $y_i$ is its ground-truth value. MAE will be reported in the units
of the task's output. Ground truth may not exist or may become available only
later. DAIIM will calculate and display MAE for available
predictions and aggregated results.

\subsection{Known Limitations}

The system aggregates provider predictions but does not independently verify
that the final result is correct. Decentralization, provider reputation, and
staking are intended to encourage reliable predictions, but the system cannot
guarantee that a result is accurate or suitable for its intended use.

\subsection{Provider Staking}

Inference providers must stake a minimum amount of tokens to register for an
inference task (\rref{FR_InferenceTaskRegistration}). The stake is locked in
escrow by the system's on-chain logic, rather than held by any person, and can
only be returned, slashed, or burned according to the rules in
\rref{FR_InferenceTaskRegistrationStaking},
\rref{FR_InferenceProviderSlashing},
\rref{FR_ProviderWillingUnregistration}, and
\rref{FR_ProviderForcedUnregistration}. Requiring a stake serves three
purposes:

\begin{itemize}
    \item \textbf{Resistance to fake accounts.} The final result is a
    reputation-weighted aggregate of provider predictions
    (\rref{FR_PredictionAggregation}), so anyone who controls enough providers
    for a task can control its results. Without a stake, an attacker could
    register many providers at no cost, and a provider with a low reputation
    could abandon their account and register a new one. Requiring a stake for
    every registration makes each additional provider cost real tokens, which
    makes gaining control of a task's results expensive.

    \item \textbf{Penalties for misbehaviour.} A loss of reputation alone may
    not deter a provider who has nothing else at risk. A stake allows the
    system to impose a financial penalty by slashing it
    (\rref{FR_InferenceProviderSlashing}), or burning it when a provider's
    reputation falls below the minimum threshold
    (\rref{FR_ProviderForcedUnregistration}).

    \item \textbf{Commitment to accepted requests.} If accepting an inference
    request had no cost, providers could accept every request and respond only
    when convenient, causing requests to be cancelled for having too few
    predictions (\rref{FR_MinimumPredictions}). Having a stake at risk gives
    providers a reason to submit a prediction for every request they accept.
\end{itemize}

A provider's stake does not determine the weight of their predictions;
reputation does (\rref{FR_PredictionAggregation}). This prevents providers from
gaining influence over results through wealth alone, so influence must be
earned through a history of predictions that agree with the network.

The minimum stake must balance two concerns. It must be high enough that
registering many fake providers is expensive, but low enough that honest new
providers, who have not yet earned any rewards, are not discouraged from
joining.

\subsection{Reputation Tolerance}

Each task specifies a reputation tolerance $T$ (\rref{FR_TaskReputationTolerance}),
and a provider's reputation only decreases when their distance from the final
aggregated result exceeds the average distance by more than $T$
(\rref{FR_ReputationDecrease}). Without this margin, roughly half of the
providers would lose reputation on every request, even when all predictions are
close together. $T$ is set per task because an acceptable margin depends on the
units and scale of the task's output.

\subsubsection{Weighted-Median Aggregation Algorithm}
\label{App_WeightedMedian}

Only valid predictions submitted by providers with a non-zero reputation score
at the end of the prediction phase are included. This reputation snapshot is
taken before any reputation updates for that inference request. Each included
prediction's weight is its provider's reputation score divided by the sum of
the included providers' reputation scores. The weights are positive and sum
to 1. \rref{FR_MinimumPredictions} requires at least the task's minimum number of included predictions
before aggregation begins.

\begin{verbatim}
Algorithm WeightedMedian
Input:  Valid predictions p[1..n] from providers with non-zero reputation,
        and corresponding normalized weights w[1..n] where each w[i] > 0
        and sum(w[i]) = 1
Output: The weighted median rounded to 4 decimal places

1.  Create a list L of pairs (p[i], w[i]) for i = 1 to n.
2.  Sort L in nondecreasing order by prediction value.
3.  Set cumulativeWeight <- 0.
4.  Set previousPrediction <- NONE.
5.  For each pair (value, weight) in L, in sorted order:
6.      previousWeight <- cumulativeWeight.
7.      cumulativeWeight <- cumulativeWeight + weight.
8.      If cumulativeWeight > 0.5:
9.          If previousWeight = 0.5:
10.             result <- (previousPrediction + value) / 2.
11.         Else:
12.             result <- value.
13.         Return result rounded to 4 decimal places.
14.     Set previousPrediction <- value.
15. Return an aggregation error.
\end{verbatim}

Read the predictions in increasing order, adding their weights as you go. The
result is the prediction where the running total first goes above 0.5. If the
running total was exactly 0.5 just before that prediction, use the average of
that prediction and the preceding prediction instead. Round the result to four
decimal places; if the value is exactly halfway between two possible rounded
values, round away from zero.
